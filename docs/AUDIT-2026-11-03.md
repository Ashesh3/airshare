# AirShare audit — November 3, 2026

## Scope and evidence

The audit started from commit `64e8756` (the initial release). The entire repository was inspected, including frontend scripts, server routes, stream lifecycle, capability boundaries, Docker packaging and documentation. An independent **Claude Opus 5.5, maximum effort** review reproduced the initial defects against private copies of that commit and reviewed the implementation and subsequent fixes. Its [full review and final acceptance](history/OPUS-REVIEW-2026-11-03.md) are retained with the project.

The reference was the live Station307 homepage, its Recipes page, its public browser bundle `DefaultTransfers.CdcjUhSp.js`, actual CLI redirect headers and a synthetic API transfer on November 3, 2026. Reference material stayed in a temporary directory; proprietary JavaScript and branding are not shipped in AirShare.

Reference pages: <https://www.station307.com/> and <https://www.station307.com/recipes>. Inspection is evidence of observable behavior, not access to or knowledge of Station307's server implementation.

The user also supplied the author's Hacker News comments from March 24–27, 2016. They confirm the original read-pausing TCP backpressure, live relay, browser reposting and terminal 307 design. The Amsterdam hosting and Java/Netty stack described there are historical context, not claims about the service's November 2026 location or implementation.

## Initial findings and remediation

| Finding in initial release | Effect | Remediation and regression evidence |
| --- | --- | --- |
| Encoded backslash/absolute static paths escaped `public/` | Unauthenticated filesystem disclosure | Resolve and check root containment, including symlinks; reject unsafe separators/encoding. Real HTTP traversal tests. |
| All role tokens resolved to the same powers; receiver HTML exposed upload/owner data | A receiver could substitute file contents or revoke someone else's channel | Distinct owner, sender, receiver capabilities, role checks on every route/alias, redacted metadata and subscription responses. Capability-forgery and leak tests. |
| Bun's implicit 128 MiB body limit | Ordinary videos/archives failed immediately | Explicit streaming ceiling plus an independent small JSON limit. Real 129 MiB regression and larger hash-checked benchmarks. |
| Raw Unicode in HTTP attachment filename | Hindi/emoji filenames caused 500s and stranded peers | ASCII fallback plus UTF-8 `filename*`, control/bidi filtering, bounded metadata; Hindi and emoji tests. |
| URLs derived from internal HTTP origin behind TLS | Browser mixed-content failures and unusable links | Validated `PUBLIC_URL`; working reverse-proxy example and public-origin tests. |
| Bun stripped `Content-Length` on streamed responses in 1.4.0 and 1.4.4 | No trustworthy download total/ETA | A streaming `node:http` adapter inside Bun preserves framing and backpressure. Raw socket tests check length, bytes and truncation. |
| Receiver-first response headers were created before the sender chose a file | Wrong filename, MIME type and size | Pending receivers are resolved against an immutable upload metadata snapshot. |
| CLI stopped after one transfer while claiming it was still hosting | Later receivers waited indefinitely | Regular files replay through 307; explicit unlimited curl redirect budget; non-replayable stdin is one-shot. Real CLI checks. |
| nginx consumed stdin before the creation redirect | A 3 MiB pipe appeared successful but delivered only about 1.81 MiB | Prepare the channel before supplying stdin, then upload directly to its sender capability; reject unprepared unknown-length creation uploads. This intentionally improves integrity over the legacy one-command redirect recipe. |
| An early redirect closed an eager Wget upload before its request body drained | Linux GNU Wget retried without receiving usable headers | Stream-discard unread redirect bodies with size/idle bounds and preserve keepalive; delay connection close until drain. Linux socket and real GNU Wget regressions. |
| Empty file rejected; extra/short bodies mishandled | Hung peers or misleading success | Zero-byte support; reject declared/actual size disagreements, withhold the final byte until valid EOF. |
| Active receivers escaped channel cleanup | Delete/abort left active requests hanging | Explicit pending/active/settled lifecycle, shared cancellation, socket close propagation. |
| All receivers leaving did not stop the upload | Unnecessary network transfer and false success | Abort the producer when its last recipient disconnects. |
| One permanently stalled multicast peer blocked everyone | Healthy receivers froze indefinitely | Bounded queues and a configurable per-receiver stall timeout; a healthy peer completes in the stalled-peer test. |
| Unbounded channel and SSE state | Memory/resource growth in a long-lived instance | SQLite metadata TTL, capacity limits, bounded status queues and cleanup on disconnect. |
| A brief reconnect could invalidate an older unused share | Created-at expiry ignored an extended period of active hosting | Measure unused expiry from the last protected period and preserve a complete reconnect grace period. |
| Global capacity let one client lock out everyone else across restarts | Thousands of unused persisted channels exhausted capacity | Per-client creation and concurrency budgets, trusted proxy opt-in, IPv6 prefix grouping, short unused lifetime and safe unused-capacity reclamation. |
| Synchronous metadata commits reduced live throughput under creation floods | Unrelated requests monopolized the event loop | WAL/NORMAL metadata writes, prepared statements, coalesced touches, admission and example proxy request limits; independent load measurements below. |
| One EventSource per shared file | HTTP/1 connection exhaustion | At most three owner event streams per page, bounded polling fallback; receive pages use polling. |
| Late receiver event raced upload completion | A complete next upload might never start | Explicit browser host state machine and post-completion reconciliation. |
| Cleanup overwrote errors or recreated removed cards | Misleading success and broken stop behavior | Persistent error state, guarded callbacks and explicit retry; frontend event-order tests. |
| Recipient cancellation ended hosting rather than serving later receivers | A live sender could be advertised while new receivers waited indefinitely | Separate retryable recipient departures from validation/network faults; CLI replay and correlated browser recovery with bounded backoff. Real curl cancellation followed by a later complete download. |
| Hardcoded localhost recipes; clipboard required secure context | Self-hosted/LAN commands and copy buttons failed | Current-origin recipes, HTTP copy fallback and visible feedback. |
| No persistent metadata or QR support | Missing advertised reference workflows | Metadata-only SQLite persistence; local SVG and terminal QR generation. |
| HTTP header normalization trimmed terminal QR rows | Unicode QR glyphs survived but no longer formed a scannable code | Guarded row whitespace plus a real HTTP roundtrip decoded by an independent QR library. |
| QR and Unicode URL headers exceeded nginx's default header buffer | CLI creation could fail with 502 on long domains or filenames | A 64 KiB header buffer, with file-body buffering disabled. A permanent compose smoke check relays the maximum 1,024-byte Unicode name on a long domain and verifies both file and prepared-stdin hashes. |
| Development error pages leaked stack/source; container ran as root | Extra exposure on input errors | Controlled 4xx/5xx, production environment, nonroot read-only app container, pinned dependency/image versions. |

The initial release should not be exposed publicly. The audit changes replace its unsafe capability and static-file behavior; retaining an old running process does not apply the fixes.

## Functional comparison

| Workflow observed in Station307 | AirShare behavior |
| --- | --- |
| Browser selects/drops one or more files | Supported with separate share cards and native `File` uploads. |
| Human receiver links and direct terminal download links | Separate role-safe links; native browser downloads. |
| Browser keeps hosting while its file remains available | Repeated complete uploads for later receivers; no server file cache. |
| Terminal starts a send or receive channel | curl/Wget entry routes and role-specific response headers. |
| Regular-file CLI hosting until stopped | 307 replay; documentation removes curl's finite default redirect budget. |
| Piped archive/encrypted/generated output | One-shot chunked upload after a preparation request. Deliberate command difference: no redirect of non-replayable stdin. |
| Several waiting receivers | A shared bounded multicast stream; late joiners wait for a complete next upload. |
| Asymmetric channel tokens | Separate creator, sender and receiver capabilities, checked server-side. |
| QR sharing | Generated on the AirShare instance, with no external QR service. |
| Persistent channel tokens, no stored file contents | SQLite metadata survives restart; streams and browser file handles do not. |
| Station-style tracker/create/subscribe/transfer API | Implemented and exercised through integration tests; not a guarantee of byte-identical undocumented behavior. |
| No fixed application file-size limit | No 128 MiB runtime default; limits remain configurable. Actual proxy/network/client limits still exist. |

## Transfer measurements

Every listed transfer used generated data and verified receiver SHA-256 against the sender. These are individual runs, not a statistically controlled comparative benchmark.

| Path | Payload | Recipients | Elapsed | Input throughput | Sampled server peak RSS |
| --- | --- | --- | --- | --- | --- |
| Live Station307 API from this machine | 4 MiB | 1 | 1.859 s | 2.152 MiB/s | Not observable |
| AirShare loopback, Windows/Bun 1.4.0 | 256 MiB | 1 | 1.14 s | 224.52 MiB/s | 64.41 MiB |
| AirShare loopback, Windows/Bun 1.4.0 | 1 GiB | 3 | 6.80 s | 150.50 MiB/s | 64.67 MiB |
| Docker/Bun 1.4.4 through nginx on this host | 256 MiB | 2 | 2.04 s | 125.31 MiB/s | Not sampled |

The three-receiver run delivered 3 GiB in total (451.50 MiB/s aggregate egress). RSS is sampled every 100 ms in the server process, separately from client hash buffers, so it is an observed sampled peak rather than a hard memory bound. Network socket/runtime buffers contribute beyond the per-stream queue budget.

**These results do not prove AirShare is faster than Station307 over the Internet.** The paths and payload sizes differ. A fair comparison must run both hosts from the same sender and receivers with the same larger payload, repeated runs and comparable concurrency. The reference server's location was not established. Self-hosting near the actual participants is a deployment choice to measure, not a speed guarantee.

## Independent transfer-under-load verification

A separate verification agent ran twelve 2 GiB uploads against fresh disk-backed loopback processes: one or three receivers, no flood or a four-worker creation/status flood, and two repeats in reversed order. All 24 receiver byte counts and SHA-256 checks matched (48 GiB received), with no observed transfer stalls or upload errors.

| Receivers | Load | Median input MiB/s | Observed range MiB/s |
| --- | --- | --- | --- |
| 1 | Baseline | 182.1 | 177.4–186.9 |
| 1 | Creation requests | 238.4 | 219.8–257.0 |
| 1 | Status requests | 232.1 | 201.8–262.4 |
| 3 | Baseline | 176.5 | 175.6–177.5 |
| 3 | Creation requests | 177.6 | 174.9–180.3 |
| 3 | Status requests | 184.1 | 180.1–188.1 |

Creation admission stayed enabled. Each creation-flood case admitted 33–35 requests and rejected 6,650–9,989 with HTTP 429; metadata grew 0.558–0.589 MiB. Highest sampled server RSS was 84.5 MiB. Flood-request p95 latency ranged from 5.43 to 8.43 ms. Separate black-box checks confirmed that an exhausted trusted client identity did not block a different identity, while forged forwarding headers from an untrusted peer could not evade its budget.

The one-receiver variation is substantial: these results do not mean flooding improves throughput. Two repeats, a repeated generated random block, client-side hashing and host scheduling are material limitations. The bounded single-identity flood is not a DDoS-resistance claim, and results do not establish WAN speeds.

## Browser checks

After the user enabled Chrome's file-upload extension permission, the actual browser UI shared a 136 MiB synthetic file named `रिपोर्ट😀-136MiB.bin` and an empty file. Two Chrome receiver pages downloaded the large file to disk. Both received 142,606,336 bytes with SHA-256 `46bca460b7eb752d23eac61b9f3b32d8b2fb7a3beb6c5b951dfd4ba23c90cc1b`, matching the source. The sender displayed two completed downloads and continued hosting. The empty file also completed through Chrome.

Reloading the sender preserved its links and correctly required reselecting the original file before hosting resumed. A rate-limited terminal receiver then cancelled after 2,111,832 bytes; Chrome reported the departure and automatically kept hosting. A subsequent Chrome receiver downloaded all 136 MiB with the same hash, without clicking Retry; the count correctly advanced to three successful downloads. Stop sharing revoked the empty-file link and the receiver disabled its download control.

A receiver-first curl command also waited while Chrome opened the generated sender page and selected a 63-byte synthetic file: the download completed with the matching hash and eventual filename. A separate actual Chrome transfer through Station307 verified the reference workflow with the same synthetic text file.

QR sharing rendered visibly. At an emulated 390-pixel viewport, the page content width equalled the viewport width, with no horizontal overflow. This is desktop Chrome responsive emulation, not an actual Android device test.

## Explicit verification limits

- Actual Chrome file transfers and responsive emulation were checked as described above. No physical Android/iOS device or Safari transfer is claimed. The user enabled the required extension file-access permission; the agent did not change browser security or certificate-trust settings.
- Frontend tests exercise actual client scripts at controlled DOM/XHR/EventSource boundaries. They cover races and UI state but cannot establish every real browser's behavior.
- nginx streaming is tested over local HTTP and Caddy over local HTTPS/HTTP/2 with an explicitly trusted test CA. A public domain, public ACME issuance, cross-country latency and the user's chosen Indian hosting provider are not provisioned or benchmarked here.
- Transfers are live and server-relayed. There is no end-to-end encryption, offline file hosting, resumable byte-range cache, distributed multi-replica stream routing or preservation of active bytes across restarts. These are explicit architectural boundaries.
- A receiver with a consistently slow connection can still pace multicast. The timeout removes stalled peers, not everyone slower than the fastest peer.
- The project is functionally compared against the observed reference, not certified as a perfect one-to-one implementation of private Station307 behavior.

Synthetic test downloads and temporary services/volumes were cleaned up. Screenshots remain as local verification artifacts.

AirShare covers the observed transfer workflows with its own branding. Piped stdin deliberately uses a preparation request to avoid redirect-related data loss. The explicit verification limits and deployment trade-offs above remain; absolute perfection or equivalence to undocumented private server behavior is not claimed.
